## Problem

OSS users who want to push feedback into attune from a JavaScript/TypeScript
runtime — a web app, an Electron app, a Node service — currently have to read the
OpenAPI doc and hand-roll `fetch` against `POST /v1/feedback/ingest`: build the
`X-API-Key` header, encode the body, parse the `{id}` response, and reinvent
retry/backoff and error handling. Every integrator pays that cost again, and any
drift between their hand-written types and the server contract is silent until
runtime.

The proto IDL contract (#19) already makes `proto/attune/v1/ingest.proto` the
single source of truth and generates TypeScript types into `console/src/proto/`.
The pieces for a typed, generated SDK exist; they are just not packaged for
external consumption. This issue ships that package.

`@phixsura/attune` is the Node/TS half of a dual SDK launch; #36 is the Go half.
The two issues stay separate, but the **retry and error semantics are defined
once here** so the two SDKs behave identically.

## Goals

- A published npm package `@phixsura/attune` wrapping the ingest API:
  `new Client({ baseURL, apiKey })` → `await client.ingest(req)` → `{ id }`.
- **Zero hand-written wire types** — `IngestRequest`/`IngestResponse` and the
  `ErrorResponse`/`ErrorCode` enum are generated from proto, regenerated by
  `make proto`, and guarded against drift by the existing `proto-sync` CI gate.
- Dual ESM-first / CommonJS-compatible output; native `fetch`, zero runtime
  dependencies; runs in Node 20+ and modern browsers.
- A retry/error contract (which status codes retry, backoff shape, typed error
  fields) that #36 (Go SDK) adopts verbatim, so both SDKs are behaviorally
  identical.
- A minimal Node example and a minimal browser example, both built in CI.

## Non-goals

- **Workflow / tag / feedback-read methods.** v1 wraps `ingest` only. The
  resource-namespace shape (`client.x.y(...)`) is left open for later additions
  but not built now (YAGNI).
- **Client-side batching / fire-and-forget queueing.** See Alternatives — the
  feedback-ingest call is transactional, not a telemetry firehose. Batching can
  be added later behind a separate option without breaking the v1 surface.
- **Automated first-publish to npm.** The first `npm publish` is manual (org +
  token bootstrap, see Risks); wiring it into the release workflow is follow-up.
- **The Go SDK (#36).** Separate issue/proposal; consumes the contract below.

## Proposal

### Package layout (in-repo, `sdk/node/`)

The SDK lives in the monorepo so it shares CI and proto generation and changes
land atomically with contract changes (the same reason the console lives in-repo).

```
sdk/node/
  package.json          # name @phixsura/attune; "type": module; exports map (import/require + types)
  tsconfig.json         # strict
  tsdown.config.ts      # dual ESM/CJS + split .d.cts/.d.mts
  src/
    index.ts            # public surface: Client, types re-export, AttuneError
    client.ts           # Client class: ingest()
    errors.ts           # AttuneError + ErrorCode mapping
    retry.ts            # shared retry/backoff (the contract below)
    proto/              # buf-generated TS types (git-tracked, make proto overwrites)
  examples/
    node-ingest/        # minimal Node script
    browser-ingest/     # minimal browser page (publishable write-key)
  test/                 # vitest: happy / 401 / validation / retry (mock fetch)
  README.md
```

### Public API

```ts
import { Client } from '@phixsura/attune'

const client = new Client({
  baseURL: 'https://attune.example.com',
  apiKey: 'ak_...',          // ingest:write scope
  // optional:
  fetch,                     // inject a custom fetch (older Node / test)
  timeout: 30_000,           // ms; default 30s
  maxRetries: 2,             // default 2
})

const { id, enrichmentStatus } = await client.ingest(
  { content, source, sourceUser, sourceMeta, pageUrl },  // IngestRequest (generated)
  { signal },                                            // optional AbortSignal
)
```

- **Transactional, await-throw model.** `ingest` resolves with the generated
  `IngestResponse` (`id` is a string per protoJSON int64 rule) or throws
  `AttuneError`. No batching, no callback, no fire-and-forget (see Alternatives).
- **Auth.** The client sets `X-API-Key: <apiKey>` on every request. Scope
  enforcement (`ingest:write`) is server-side; the SDK only carries the key.
- **Runtime.** Uses `globalThis.fetch`; the `fetch` option overrides it. No
  axios / node-fetch / undici dependency.

### Type generation

`buf.gen.yaml` gains a second `ts-proto` output target writing to
`sdk/node/src/proto/` with the same options the console target uses
(`onlyTypes=true`, `forceLong=string`, `stringEnums=true`). `make proto`
regenerates both targets; the `proto-sync` CI gate already fails on drift, so the
SDK types track the contract automatically. `onlyTypes=true` means the generated
`.ts` compile to pure type declarations (no runtime JS), so generating the full
message set into the package carries no runtime weight.

### Retry / error contract (shared with #36)

This section is the normative contract both SDKs implement.

- **Retry on:** network/connection errors, request timeout, HTTP `408`, `429`,
  and `5xx`.
- **Never retry:** `400`, `401`, `403`, `404`, `409`, `422`, and other 4xx —
  deterministic client errors. ingest's only `409` is `IDEMPOTENCY_CONFLICT`
  (same key + different body), which is permanent; there is no in-progress 409
  (the server's unique index serializes concurrent same-key retries internally).
- **Retry safety:** ingest is a non-idempotent POST, so retrying a request that
  the server already processed (lost response, timeout, proxy 5xx) would
  duplicate a feedback row. The SDK makes retries safe with an idempotency key —
  see the Idempotency section below; the retry policy above depends on it.
- **Attempts:** `maxRetries` default **2** (1 initial + 2 retries). Matches the
  OpenAI/Anthropic TS SDKs, whose Go counterparts attune already depends on.
- **Backoff:** exponential, base 200ms, cap 2s, with ±25% jitter. If the
  response carries `Retry-After` (seconds or HTTP-date), honor it (clamped to a
  max wait) in preference to the computed delay.
- **Timeout:** default 30s per attempt, via `AbortSignal`; a timeout is itself a
  retryable error.
- **Error type:** `AttuneError extends Error` with fields `code` (the
  `ErrorResponse.code` enum value), `status` (HTTP status), `requestId` (from the
  error envelope), and `headers`. Network/timeout failures surface as
  `AttuneError` with a synthetic code (e.g. `NETWORK` / `TIMEOUT`). Non-2xx
  responses parse the unified `{ code, message, requestId }` envelope.

### Idempotency (server + SDK)

Because ingest is a non-idempotent POST, safe retries require server cooperation.
The dedup point is a **partial unique index** on the insert itself — the only
mechanism that is correct under concurrency (a check-then-insert, or reusing the
`idempotency_keys`/`Acquire` machinery whose pending state returns
`acquired=true`, both let two simultaneous retries each insert a row).

- **Schema (migrations 055–056):** `user_feedback` gains nullable
  `idempotency_key` + `idempotency_hash` columns (055, metadata-only) and a
  partial unique index `(tenant_id, idempotency_key) WHERE idempotency_key IS
  NOT NULL` built `CONCURRENTLY` (056), so deploying it does not lock ingest on a
  large table. CONCURRENTLY cannot run in a transaction, so the migration runner
  gained a `-- migrate:no-transaction` directive for single-statement,
  idempotent migrations.
- **Server (`repo/feedback.InsertIdempotent`):** `INSERT … ON CONFLICT
  (tenant_id, idempotency_key) DO NOTHING RETURNING id`. A fresh insert returns
  its id. On conflict it reads the existing row back and compares
  `idempotency_hash`: a matching fingerprint is a **dedup** (returns the original
  id, no new row, no second enrichment); a differing fingerprint is
  `409 IDEMPOTENCY_CONFLICT`; a malformed key is `400 VALIDATION`. Under
  concurrency the loser's INSERT blocks on the unique index until the winner
  commits, then takes the conflict path — so N simultaneous same-key retries
  collapse to one row, with **no in-progress 409** bounced to the client. The
  key is read from the `Idempotency-Key` header (not the proto body) and carried
  on `domain.IngestInput`, so inbound adapters (#66) pass none → unchanged path.
- **SDK:** every `ingest()` call sends a UUID `Idempotency-Key`, **held stable
  across that call's retries**; callers can pass their own `idempotencyKey`.

This expands #37 from "SDK only" to "SDK + ingest idempotency" — the only way to
keep the resilient retry contract above without risking duplicate rows, verified
by a live 8-way-concurrent e2e that asserts exactly one row.

### Browser support — publishable write-key model

The ingest endpoint backs an in-app web widget (`source: "web"`, `pageUrl`), so
browser use is a first-class case. `ingest:write` API keys are treated as
**publishable credentials** — like a Segment write key, a Sentry DSN, or a
Supabase anon key — relying on attune's existing per-key controls (rate limits,
IP allowlist, narrow scope) rather than a secrecy assumption. The SDK therefore
works in the browser with no `dangerouslyAllowBrowser`-style gate; the README
states plainly that an `ingest:write` key is public and must be rate-limited /
IP-scoped, and that secret-grade keys (broader scopes) must never ship to a
browser. `examples/browser-ingest/` demonstrates the widget pattern.

### Build / test / CI / publish

- **Build:** `tsdown` produces ESM + CJS + split `.d.cts/.d.mts`. (Resend and
  Supabase — the closest-profile modern SDKs — both use tsdown; see References.)
- **Tests:** Vitest (matches the console). Unit cases: happy path, 401, a
  validation 4xx (no-retry assertion), and a retry path (mock `fetch` returning
  429→200, asserting attempt count and `Retry-After` honoring). `tsc --strict`
  passes.
- **CI:** a new job builds the SDK, runs `tsc` + vitest, and builds both
  examples; hung off the existing `ci-gate` aggregation.
- **Publish:** first `npm publish @phixsura/attune` is manual (org + token
  bootstrap); a follow-up wires it into the release workflow.
- **Changelog:** one `### Added` entry under `[Unreleased]`.

## Alternatives considered

- **Batched, fire-and-forget ingestion (Segment / PostHog / Sentry model).**
  Those high-volume telemetry SDKs enqueue events, flush on a size/time
  threshold, surface errors out-of-band via an `EventEmitter`, and require an
  awaited `shutdown()` drain — because dropping telemetry must never crash the
  host. attune feedback is the opposite: each item is a user-meaningful action,
  the endpoint returns a row `id` synchronously, and the issue specifies
  `ingest(req): Promise<{id}>`. Rejected for v1; the transactional model
  (Resend / OpenAI shape) fits. Batching remains addable later behind an option.

- **External repo `github.com/Phixsura/attune-node`.** Cleaner npm-only release
  surface and the common OSS convention, but proto types would have to cross
  repos (submodule or a published intermediate package) and the work would fall
  outside attune's proposal/CHANGELOG/CI flow. Rejected — in-repo keeps the
  contract and the SDK in lockstep; we can extract later if release cadence
  demands it.

- **Reuse `console/src/proto` types directly.** Avoids a second generation
  target, but couples the published package to the console's directory layout and
  crosses a package boundary that does not exist today. Rejected in favor of a
  dedicated `buf.gen` target.

- **`tsup` for the build.** The original pick, but none of the ten benchmarked
  SDKs use it; tsdown is its rolldown-based successor and is what the two
  closest-profile recent SDKs (Resend, Supabase) adopted. Chose tsdown.

- **`dangerouslyAllowBrowser` gate (OpenAI / Anthropic model).** Appropriate
  when the key is secret-grade. attune's `ingest:write` key is scoped and
  rate-limitable, making the publishable-write-key model (Segment / Sentry /
  Supabase) the better fit for the web-widget use case. Rejected in favor of
  documented publishability.

## Risks / tradeoffs

- **Retrying a non-idempotent POST.** Found during verification: without server
  cooperation, a retry of a request the server already processed duplicates a
  feedback row — including the concurrent case (timeout → immediate retry while
  the first is still in flight), which a first idempotency attempt using
  `idempotency_keys`/`Acquire` did NOT cover (its pending state returns
  `acquired=true`, so both retries insert). Mitigation: the partial-unique-index
  dedup above is atomic under concurrency; proven by an 8-way-concurrent live
  e2e that asserts exactly one row.
- **Scope expansion + core-table migration.** #37 now adds two nullable columns
  + a partial index to `user_feedback` and touches the ingest handler/service.
  Mitigation: columns are nullable (backward-compatible); inbound adapters pass
  no key → unchanged insert path; covered by new unit + live (incl. concurrent)
  e2e tests.
- **Publishable write-key messaging.** If users ship a broad-scope key to the
  browser thinking it is safe, that is a leak. Mitigation: README is explicit
  that only `ingest:write` keys are publishable and must be rate-limited /
  IP-scoped; the browser example uses such a key.
- **Node build artifact in a Go-primary repo.** Adds a Node CI job and an npm
  publish path. Mitigation: scoped to `sdk/node/`, hung off the existing
  `ci-gate`, mirroring how the console already coexists.
- **Manual first publish.** The npm org/token bootstrap is a one-time manual
  step; until automated it is a release-process footgun. Mitigation: documented
  as follow-up; the package builds and tests in CI regardless.
- **Deviations from the issue text** (called out per CLAUDE.md hygiene): Node
  floor 18 → 20 (Node 18 is EOL as of 2025-04 and every benchmarked modern SDK
  is on 20); added a `browser-ingest` example plus write-key security docs beyond
  the issue's single `node-ingest` example.

## Implementation plan

1. **Proto target.** Add the `sdk/node/src/proto` ts-proto target to
   `buf.gen.yaml`; run `make proto`; commit generated output.
2. **Package skeleton.** `sdk/node/` with `package.json`, `tsconfig.json`,
   `tsdown.config.ts`, exports map.
3. **Core.** `errors.ts` (AttuneError + ErrorCode mapping), `retry.ts` (the
   contract above), `client.ts` (`ingest`, portable timeout/abort via
   AbortController, auto `Idempotency-Key`), `index.ts` (public surface).
4. **Ingest idempotency (server).** Migration 055 (idempotency columns + partial
   unique index); `repo/feedback.InsertIdempotent` (ON CONFLICT DO NOTHING +
   fingerprint compare); `domain.IngestInput.IdempotencyKey` from the header;
   `service.Ingestor` routes to it and maps conflict → 409.
5. **Tests.** Vitest unit (happy / 401 / validation-no-retry / 429-retry /
   network / timeout / abort / idempotency-key) + Go unit (ingestor dedup /
   conflict / in-progress / malformed-key; handler 409 mapping); `tsc --strict`.
6. **Examples.** `examples/node-ingest/` and `examples/browser-ingest/`.
7. **CI.** New job: build + tsc + vitest + example builds, under `ci-gate`.
8. **Live e2e.** `test/e2e` + `scripts/e2e.sh` (boots Postgres + server, runs the
   suite incl. idempotency, asserts DB dedup).
9. **Docs.** SDK `README.md` (write-key publishability + idempotency note); root
   `CHANGELOG.md` `### Added`.
